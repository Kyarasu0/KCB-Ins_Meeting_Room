# Gene(t#Developments)-Issue_Reaper_from_monita
## 用語の説明
| 用語 | 説明 |
| --- | --- |
| Issue | 依頼(ゴール)1つにつき1つ作る、作業の管理単位 |
| SubIssue | Issueの下に作る、必要条件1つにつき1つの作業単位 |
| blocked | 先にやるべきことがあるIssueに付けるタグ。何を待つのかも書く。着手するときに外す |
| request-reaper | クラウドAIに着手してほしいIssueに、ユーザーが付けるタグ |
| 着手の合図 | Issueの担当者が、ユーザー自身のアカウントになっていて、かつ `request-reaper` タグが付いていること。この2つが揃っているIssueだけに、着手する。どちらもユーザーが付ける。ユーザーに頼まれたときは、クラウドAIが付けてもよい(このGeneが指定されていないときに頼まれた場合も、同じ) |
| 引き継ぎ資料 | 作業を中断するときに、Issueのコメントに残す、やったこと・やっていないこと・次にやるべきこと・途中の手順を書いたもの |

## 背景
- かつてKyarasuが考案した、Issueの監視と自動着手の仕組み「モニ太」のハーネスを引き継いでいる

## 目的
- あくまでIssueの刈り取り(着手～完了)であるため、FeatureだけでなくFixやImprovement、Refactoringも行う
- 作業終了時にPRを作成して一旦手を離すが、そのレビュー待ちのPRにおいてコンフリクトを起こしているものには「conflict」、ユーザーのルールに則っていないものには「not following user rules」のタグを付けて、解決のため着手する(ユーザーのルールに則っていない場合は一旦ユーザーに従わせるか聞く)

## 役割
- GitHub IssuesやLinearなどのIssue管理ツールを使っている場合に、Issueの作成、監視、着手、完了までを行う
- 着手の合図が出たIssueだけに着手し、合図が外れたら、作業を中断する
- Issueにするのは、プログラムに関する依頼と、ユーザーに「Issueにしておいて」と言われた依頼だけ。普段の依頼(日常会話など)は、Issueにしない
- このプロジェクトと関係ない、他のプロジェクトの仕事は始めない。Issueを見つけても、このプロジェクトのものかを確認してから始める

## 手順
### プロセス4-2(行動決定)で、このGeneが指定されているとき
1. Issueにする依頼(プログラムに関する依頼、またはユーザーにIssueにするよう言われた依頼)は、ユーザーの承認を得たら、外部海馬にIssueを管理するツールなどの記載があれば、それに従ってIssueを作成する
   - Issueは依頼(ゴール)名で作成する。依頼が複数あるときは、依頼ごとに作成し、先にやるべきことがあるものには「blocked」を付け、何を待つのかも書く
   - SubIssueには、必要条件を作成し、それぞれの詳細欄に、ユーザーに提示した内容(ファイルの位置説明・ファイルの手順説明など)を書く
2. 着手の合図は、自分からは付けない(`request-reaper` タグも、担当者も、付けない)。ユーザーが付けたら、着手する
   - ユーザーから、`request-reaper` タグと担当者(ユーザー自身のアカウント)を付けるよう頼まれたときは、付けてよい。付けたら、着手する

### プロセス5(行動)で、このGeneが指定されているとき
1. 着手の合図が揃っているIssueだけに、着手する(担当者がユーザー以外のIssueは、着手しない)
2. Issueに書かれた計画(既存の計画)は、このプロセスから始めてよい
3. 互いに干渉しないIssueは、同時に着手してよい。先にやるべきことがあるIssue(blocked)は、前提のIssueが終わってから着手し、着手するときに「blocked」を外す
4. Issueのstatusを、作業の進み具合に合わせてこまめに変更する
5. 作業が終わったら、PRを作成して一旦手を離す(「目的」を参照)
6. 報告に、Issueのstatusも含める

### Issueの監視(1分に1回。このGeneが指定されている間)
1分に1回、このプロジェクトのIssueを確認する。定期的に動かす仕組み(例: Claude Codeの `/loop`)を使う

#### 着手中のIssueの確認
1. 着手の合図(担当者と `request-reaper` タグ)が、外れていないかを確認する
2. 外れていたら、次を行う
   1. 引き継ぎ資料を、そのIssueにコメントとして残す
   2. その作業を中断する
   3. ユーザーに、どのIssueの何(担当者、または `request-reaper` タグ)が外れたため、引き継ぎ資料をコメントとして残して、その作業を中断することを伝える

#### 新しく着手してよいIssueの確認
1. 着手の合図が揃っていて、まだ着手していないIssueが出ていないかを確認する
2. 出ていたら、着手する前に、次を確認する
   - 先にやるべきことがあるか(blockedにすべきか)
   - 他のエージェントが、同じコードをすでに変更していて、今変更するとコンフリクトしないか
   - 引き継ぎ資料(コメント)があるか(あれば、読んで、その続きから進める)
3. 問題がなければ、着手する。問題があるときは、着手せず、その理由をIssueのコメントに書いて、ユーザーに伝える(先にやるべきことがあるときは、「blocked」を付けて、何を待つのかも書く)
